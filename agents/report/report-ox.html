2. Agent Loop — Session Runner

2.1 双层循环

// packages/core/src/session/runner/llm.ts

const run = Effect.fn("SessionRunner.run")(function* (input) {
  let shouldRun = input.force || hasSteer || hasQueue
  let promotion: "steer" | "queue" | undefined

  while (shouldRun) {                          // 外层：处理输入队列
    let needsContinuation = true
    let step = 1
    while (needsContinuation) {                // 内层：agent 循环
      const result = yield* runTurn(sessionID, promotion, step)
      needsContinuation = result.needsContinuation  // 工具调用 → 继续
      step = result.step + 1
      promotion = "steer"
      if (!needsContinuation)
        needsContinuation = yield* SessionInput.hasPending(db, sessionID, "steer")
    }
    shouldRun = yield* SessionInput.hasPending(db, sessionID, "queue")
  }
})

2.2 runTurn — 单次 LLM 调用 + 工具执行

runTurn(): ① 加载 session, agent, model, system context ② 检查 step 限制: isLastStep? → 是: 禁用工具，追加 MAX_STEPS_PROMPT ③ 构建 LLM request: system + messages + tool definitions ④ llm.stream(request) → 流式获取 LLM 响应 ⑤ 每收到 tool-call → toolMaterialization.settle() 并发执行 ⑥ 等待所有 FiberSet 完成 ⑦ 返回 { needsContinuation, step } 异常处理: TurnTransitionError.OverflowCompaction → 压缩后继续 其他 defect → Effect.die

2.3 Steer vs Queue 投递模式

模式行为
Steer在下一个安全的 provider-turn 边界插队，当前 drain 继续
Queue保持挂起直到 session 会空闲时才处理

这是 OX 独有概念：用户可以在 agent 执行中间插入"转向"指令。

2.4 退出条件

退出类型触发条件
正常完成模型不返回工具调用 + 无 steer/queue
Step 上限达到 agent 配置的 steps 限制 → 禁用工具
用户中断failInterruptedTools()
Overflow Compaction上下文溢出 → 压缩后继续

4. 记忆机制

OpenCode 没有独立的跨会话记忆系统（不像 CC 的 CLAUDE.md 或 CX 的两阶段记忆管线）。它通过以下机制间接实现：

4.1 配置文件指令

// opencode.json
{
  "instructions": ["./INSTRUCTIONS.md", "https://..."],
  // 路径或 URL 指向持久化指令文件
}

4.2 Session Context Epoch（会话上下文快照）

恢复会话时，比较当前 SystemContext 与存储的 snapshot，仅发送 delta：

prepareOnce():
  if (!stored) → SystemContext.initialize() → 写入新快照
  if (stored)  → SystemContext.reconcile(current, snapshot)
              → 仅变化的 source 生成更新文本

4.3 Compaction Summary 作为记忆

compaction 产生的结构化摘要存储在 session_message 表中，作为对话的压缩记忆。

6. 状态管理

6.1 分布式 Effect 服务

没有独立的 state 包。状态分散在 Effect 服务中：

服务职责
SessionExecution进程全局协调（active/resume/wake/interrupt）
SessionRunner实际 agent 循环
SessionStore会话读取（get/context/runnerContext）
SessionProjector事件 → SQL 投影
MessageUpdater内存消息状态（Immer 不可变）

6.2 SessionExecution 接口

interface SessionExecution {
  active: Effect<ReadonlySet<SessionID>>         // 当前活跃会话
  resume(sessionID): Effect<void, RunError>      // 加入或启动执行
  wake(sessionID): Effect<void>                  // 建议性唤醒
  interrupt(sessionID): Effect<void>             // 中断执行
}

7. 安全机制

7.1 三值权限模型

type Effect = "allow" | "deny" | "ask"

evaluate(action, resource, ...rulesets):
  → findLast 匹配的规则 → 未匹配则默认 "ask"

assert(input):
  effect === "deny"  → throw BlockedError
  effect === "allow" → 继续
  effect === "ask"   → 创建 pending 请求 → 阻塞等待用户回复

7.2 权限来源优先级

配置的 agent rules (最高) ├─ deny 优先于 saved allow ↓ saved rules ("always allow" 持久化) ↓ 默认 "ask"

7.3 路径隔离 — LocationMutation

resolve(input):
  relative path 逃逸 location → PathError("relative_escape")
  absolute path 在 location 外  → 需要 external_directory 权限
  symlink 指向 location 外     → PathError("location_escape")

7.4 工具注册权限过滤

ToolRegistry.materialize() 时过滤掉被 deny 的工具（目录级可见性控制），但运行时仍依赖 assert()。

7.5 保存的权限

用户回答"always"时存入 permission SQLite 表（按 project + action + resource 唯一索引）。

8.1 双层注册

Location-scoped built-ins → Tools.Service.register() (bash, edit, read, write, glob, grep, ...) ↓ Process-scoped application tools → ApplicationTools.Service (plugins/external tools) ↓ ToolRegistry.materialize(permissions?) → 合并两层 + 过滤 deny → Materialization ├─ definitions: ToolDefinition[] (给 LLM) └─ settle(): (call) → Settlement (执行工具)
