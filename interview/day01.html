Day 01 - Agent 架构设计：从"聊天机器人"到"能干活的系统"

中级 字节 阿里 腾讯 蚂蚁

1. 核心面试题：Chatbot 和 Agent 的本质区别是什么？

Chatbot 和 Agent 的本质区别是什么？加工具的 Chatbot 就是 Agent 吗？

Chatbot = 单轮问答：user → LLM → response。每次输入独立，模型给出回答后流程结束。

Agent = 多轮推理行动循环：user → LLM → tool → LLM → ... → response。模型可以主动调用工具、观察结果、再决策，形成一个 while 循环，直到任务完成或满足终止条件。

Chatbot: User ──→ LLM ──→ Response Agent: User ──→ LLM ──→ Tool Call ──→ Tool Result ──→ LLM ──→ ... ↑ │ └─────────── 继续推理 ←────────────────────┘ (直到 stop_reason=end_turn 或其他终止条件)

关键差别在于：控制流是线性的还是循环的。Agent 的核心是 ReAct（Reasoning + Acting）循环——模型不只答一次，而是"想一步、做一步、看结果、再想"。

很多人说"Agent 就是加了工具的 Chatbot"——错！核心区别不在工具，在循环。加工具但不给循环能力的叫 Tool-augmented Chatbot，不是 Agent。比如一个只做单轮 function calling 的问答系统，虽然有工具，但流程是线性的，这不叫 Agent。

真正的 Agent 必须满足：模型可以自主决定是否继续调用工具、何时停止，而不是由外部逻辑硬编码"调用一次工具就返回"。
如果 Agent 的循环是核心，那循环什么时候结束？如果 LLM 一直不停调用工具怎么办？

→ 这就是为什么需要终止条件（见第 3 题）和熔断机制（circuit breaker）。循环是 Agent 的力量，失控的循环是 Agent 的灾难。
在 CC 源码中，这个循环的实现在 query.ts 的核心函数里。你可以在源码中搜索 stop_reason 关键字，看到循环退出的多种条件判断。Chatbot 模式对应的是只走一次循环就退出的特例。

2. CC 的三层架构：为什么这么分？

Claude Code 的架构是怎么分层的？为什么不把所有逻辑放在一个模块里？
CC 采用三层架构，每层职责明确：
┌─────────────────────────────────────────────────┐ │ QueryEngine（管家 / 指挥层） │ │ - 管理 mutableMessages（对话历史） │ │ - 管理 abortController（中断控制） │ │ - 管理 usage（token 用量统计） │ │ - 管理权限记录（tool 权限 white/blacklist） │ │ - 不做业务逻辑决策 │ ├─────────────────────────────────────────────────┤ │ query.ts（调度层 / 核心引擎） │ │ - 组装消息（system prompt + history + tools） │ │ - 驱动 ReAct 循环 │ │ - 处理工具执行结果 │ │ - 决策：继续循环 / 压缩 / 终止 │ │ - 不存状态、不关心 HTTP │ ├─────────────────────────────────────────────────┤ │ claude.ts（通信层） │ │ - 发 HTTP 请求到 Anthropic API │ │ - 处理流式响应（SSE parsing） │ │ - 返回结构化结果 │ │ - 不知道对话历史、不知道工具逻辑 │ └─────────────────────────────────────────────────┘

设计原则：单一职责

  • QueryEngine 不知道 HTTP 细节
  • claude.ts 不知道对话历史
  • query.ts 不知道 UI 怎么渲染
为什么不直接让 QueryEngine 调 claude.ts？省掉中间的 query.ts 不是更简单？

→ 因为中间状态需要有人处理。在 ReAct 循环中，工具执行后需要决策"继续循环还是压缩对话"，对话超长需要触发 compact，多次压缩失败需要熔断。这些调度逻辑不属于状态管理（QueryEngine），也不属于通信（claude.ts），所以必须有独立的调度层。

如果把调度逻辑塞进 QueryEngine，它就变成了"既管状态又做决策"的 God Object；塞进 claude.ts，通信层就耦合了业务逻辑——两者都违反单一职责。
在源码中跟踪调用链：
QueryEngine 创建 → 调用 query()（query.ts）→ 内部调用 claude()（claude.ts）→ 返回结果 → query() 判断是否继续循环 → 如需继续，再调 claude()

注意 QueryEngine 的角色：它在循环之外，持有整个会话的状态。循环之内的每一次迭代，query.ts 从 QueryEngine 读状态、写状态，但决策逻辑在 query.ts 自身。

3. 手写简化 ReAct 循环

请写出 Agent 的 ReAct 核心循环的伪代码，并说明所有可能的终止条件。 
// 简化版 ReAct 循环
async function reactLoop(messages, tools) {
  let consecutiveFailures = 0

  while (true) {
    // 1. 调用 LLM
    const response = await claude(messages, tools)

    // 2. 将 LLM 输出追加到消息历史
    messages.push(response)

    // 3. 检查终止条件
    if (response.stop_reason === 'end_turn') {
      break  // LLM 认为任务完成，正常退出
    }

    // 4. LLM 请求调用工具
    if (response.stop_reason === 'tool_use') {
      const toolResults = await executeTools(response.tool_calls)
      messages.push({ role: 'user', content: toolResults })

      consecutiveFailures = 0  // 工具执行成功，重置计数
      continue  // 回到循环顶部，让 LLM 看到工具结果
    }
  }
}

5 个终止条件：

终止条件 触发原因 源码对应
end_turn LLM 判断任务完成，主动停止 stop_reason === 'end_turn'
用户中断 用户按 Esc / Ctrl+C 强制中止 abortController.abort()
API 错误 网络异常、额度用尽、服务不可用 catch 块中的错误处理
3x 压缩失败（熔断） 连续 3 次对话压缩失败，触发熔断器 consecutiveFailures >= 3
maxTurns 超限 循环轮次超过用户设定的上限 turnCount >= maxTurns
熔断器的 consecutiveFailures 是跨 turn 的还是单次重试的？

→ 跨 turn 的。它统计的是连续的 turn 级别失败，不是单次 HTTP 请求的重试。每次 ReAct 循环中，如果压缩请求本身也超长（prompt_too_long），意味着连压缩请求本身都发不出去——这是最严重的状态，说明对话已经膨胀到无法挽救，必须熔断。

注意：consecutiveFailures 每次工具执行成功后会重置为 0。只有压缩失败的 turn 才会计数。这是一种"可恢复的熔断"——中间如果有成功的 turn，计数就归零。
在 CC 源码中找到完整循环实现，注意以下细节：
1. stop_reason 的判断不止 end_turn 和 tool_use，还有 max_tokens（输出被截断）
2. 工具执行有超时控制和权限检查
3. 压缩逻辑（compact）不是每次循环都触发，而是对话长度超过阈值时才触发
4. 循环内还有 token 用量统计和费用估算

4. 设计题：如果要你从零设计一个 Agent 系统，你会怎么分模块？

如果从零设计一个 Agent 系统，你会怎么划分模块？为什么？
基于 CC 源码的实践，一个 Agent 系统至少需要 6 个模块：
┌──────────────────────────────────────────────────────┐ │ 用户输入层 (REPL) │ │ - 接收用户输入 / 斜杠命令 / 中断信号 │ ├──────────────────────────────────────────────────────┤ │ 编排层 (query.ts) │ │ - 组装消息、驱动 ReAct 循环、处理分支逻辑 │ │ - 决策但不存状态 │ ├──────────────────────────────────────────────────────┤ │ 状态层 (QueryEngine) │ │ - 对话历史、中断控制、用量统计、权限记录 │ │ - 存状态但不决策 │ ├──────────────────────────────────────────────────────┤ │ 通信层 (claude.ts) │ │ - HTTP 请求、流式解析、重试/超时 │ ├──────────────────────────────────────────────────────┤ │ 工具层 (tools/) │ │ - 各工具的实现与注册（Read/Write/Bash/Glob...） │ │ - 工具权限与校验 │ ├──────────────────────────────────────────────────────┤ │ 压缩层 (compact/) │ │ - 对话摘要、上下文裁剪、token 预算管理 │ └──────────────────────────────────────────────────────┘

最关键的设计洞察：状态和逻辑分离

  • QueryEngine 存状态但不决策——它是"账本"，只记录事实
  • query.ts 决策但不存状态——它是"大脑"，只做判断

这种分离的收益：

  • 易测试：决策逻辑可以纯函数测试，不需要 mock 状态
  • 易替换：换 LLM 提供商只改通信层，换压缩策略只改压缩层
  • 易调试：状态层可以导出快照，复现问题
如果未来要支持多 Agent 协作（多个 Agent 共同完成任务），这个架构需要怎么改？

→ 状态层需要从"单 Agent 会话状态"扩展为"多 Agent 共享状态"——包括共享的消息队列、任务分配表、锁机制。编排层需要支持跨 Agent 的任务调度和结果汇总。通信层不变，工具层需要增加 Agent 间通信的工具（如 delegate_task、report_result）。

CC 目前的架构是为单 Agent 设计的，但分层设计让多 Agent 扩展成为可能——关键就是状态和逻辑的分离，让编排层可以从"单循环"升级为"多循环协调"。
在 CC 源码中验证这个模块划分：用 grep 搜索各模块的入口文件，确认职责边界是否如上所述。特别关注 query.ts 中是否有"不该有的"状态修改（比如直接修改 messages 而不是通过 QueryEngine），以及 claude.ts 中是否有业务逻辑泄露。

Day 01 小结

今日核心收获：

  1. Agent ≠ Chatbot + 工具。Agent 的核心是自主循环，工具只是手段
  2. CC 三层架构的精髓：单一职责 + 状态与逻辑分离
  3. ReAct 循环有 5 种终止条件，熔断器保护系统不死循环
  4. 从零设计 Agent 系统：6 模块，核心是"账本"和"大脑"的分离
