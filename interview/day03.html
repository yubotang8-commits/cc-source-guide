中级 字节 阿里 快手 腾讯

一、发给大模型的完整请求到底长什么样？

Claude Code 调用 Anthropic API 时，发给大模型的完整请求体包含哪些顶层字段？它们各自的职责是什么？

Anthropic Messages API 的请求体有三个独立的顶层字段，而非把所有东西都塞进一个字符串：

  • system — 系统提示词字符串。包含角色定义、行为准则、工具使用规则、系统上下文（如 cwd/git status）、用户记忆、CLAUDE.md 注入内容等。
  • tools — 工具定义数组。每个元素包含 name、description、input_schema，是结构化的 JSON Schema 定义。工具描述不在 system 字段里。
  • messages — 消息历史数组。严格按 user/assistant 交替排列，承载对话上下文和工具调用结果。
Anthropic API 请求体结构 ========================= { system: "你是 Claude Code，一个终端编程助手...（角色+规则+上下文+CLAUDE.md）", tools: [ { name: "Read", description: "读取文件...", input_schema: {...} }, { name: "Write", description: "写入文件...", input_schema: {...} }, { name: "Bash", description: "执行命令...", input_schema: {...} }, ... ], messages: [ { role: "user", content: "帮我读一下 main.ts" }, { role: "assistant", content: [{ type:"tool_use", name:"Read", input:{...} }] }, { role: "user", content: [{ type:"tool_result", tool_use_id:"...", content:"..." }] }, ... ] } 关键字：三个字段，各司其职，互不包含

"工具描述在系统提示词最后面" — 错！

工具定义在独立的 tools 字段中，系统提示词里只有工具使用规则（如"优先用 Read 读文件而不是 Bash cat"），而不是工具的结构化定义。这是两码事：

  • tools 字段 = 工具的"接口定义"（name/description/schema），API 可以解析和校验
  • system 字段 = 工具的"使用策略"（什么场景用什么工具、什么操作被禁止），是自然语言规则

混淆这两者会导致面试官认为你不理解 API 的设计意图。

为什么要这样分离？合并成一个 system 字段不行吗？

  • API 层面的工具调用校验：独立 tools 字段让 API 能验证模型返回的 tool_use 是否是已定义的工具、参数是否符合 schema。如果工具定义混在 system 文本里，API 根本无法做结构化校验。
  • Prompt Caching 分离缓存：tools 定义通常很稳定（一次会话中不变），可以单独缓存；system 的动态部分每次可能变化。分离后 API 可以对 tools 做独立缓存，减少 token 计费。
  • 防止工具幻觉：API 知道有哪些工具，当模型试图调用不存在的工具时可以拦截。如果工具定义只是 system 文本中的一段话，模型完全可以"编造"一个不存在的工具。

在 CC 源码中，定位以下关键位置：

  • src/core/claude.ts — querySonnet() 函数，查看 API 调用时如何组装 system / tools / messages 三个字段
  • src/core/tools/ — 各工具的 description 和 inputSchema 导出，这些才是 tools 字段的内容
  • src/core/prompts/system.ts — 系统提示词的拼接逻辑，注意里面只有工具使用规则，没有工具 schema

二、系统提示词为什么要分段？static/dynamic boundary 有什么意义？

Claude Code 的系统提示词内部用了 SYSTEM_PROMPT_DYNAMIC_BOUNDARY 做分隔，这个设计背后的动机是什么？如果不懂 Prompt Caching 能理解这个设计吗？

系统提示词被显式分为两段：

  • Static 段（boundary 之前）：模型身份定义、安全规则、编程风格偏好、基础工具使用指南。内容极少变化，缓存命中率极高。
  • Dynamic 段（boundary 之后）：当前工作目录、git 状态、MCP 服务器指令、用户配置。每次请求都可能不同，缓存命中率低。
system 字段内部结构 ==================== ┌──────────────────────────────────────────────────┐ │ Static 段 │ │ ┌──────────────────────────────────────────────┐ │ │ │ 模型身份：你是 Claude Code... │ │ │ │ 安全规则：不能破坏用户代码... │ │ │ │ 编程风格：先读后写、增量编辑... │ │ │ │ 基础工具指南：优先 Read > Bash cat... │ │ │ └──────────────────────────────────────────────┘ │ │ │ │ SYSTEM_PROMPT_DYNAMIC_BOUNDARY │ │ │ │ Dynamic 段 │ │ ┌──────────────────────────────────────────────┐ │ │ │ cwd: /home/user/my-project │ │ │ │ git branch: feature/login │ │ │ │ MCP servers: [postgres, github] │ │ │ │ 用户配置: { preferredEditor: "vim" } │ │ │ └──────────────────────────────────────────────┘ │ └──────────────────────────────────────────────────┘ Prompt Caching：Static 段被缓存 → 省钱 + 省延迟 Dynamic 段每次重新计算 → 付出代价最小

如果你在系统提示词的 static 段里嵌入了当前时间戳，会发生什么？

每次请求时 static 段的内容都变了 → 缓存 key 不匹配 → 缓存永远命中不了 → 每次都要重新处理整个 static 段的 token → 成本和延迟都上升。

这就解释了为什么 CC 把时间相关的动态信息放在 boundary 之后：保证 static 段的"静态性"是缓存有效的前提。

更一般的启示：设计系统提示词时，必须区分"会变的信息"和"不变的信息"，把它们分开存放，这是 Prompt Caching 的基本功。

  • src/core/prompts/system.ts — 查看 boundary 前后分别拼接了哪些内容
  • 对照 Anthropic API 的 cache_control 参数，看 CC 如何为 static 段设置缓存标记
  • 试试在 static 段加入一个动态值（如 Date.now()），观察 prompt cache hit rate 的变化

三、CLAUDE.md 注入机制 vs 配置优先级

CLAUDE.md 文件的加载顺序是什么？多个 CLAUDE.md 之间是覆盖还是合并？CLAUDE.md 的优先级和 CLI 配置的优先级有什么本质区别？

CLAUDE.md 加载顺序（从远到近）：

  1. Managed CLAUDE.md（组织级管理员下发）
  2. User CLAUDE.md（~/.claude/CLAUDE.md，用户全局偏好）
  3. 项目根目录 CLAUDE.md（repo_root/CLAUDE.md，项目规范）
  4. 子目录 CLAUDE.md（沿途每一级目录）
  5. CWD 的 CLAUDE.md（当前工作目录，最近）

多个 CLAUDE.md 的关系：全部注入，由模型裁决（soft merge）。

不会互相覆盖。所有层级的 CLAUDE.md 内容都会拼接进系统提示词，模型同时看到所有指令，自行判断如何处理冲突。这是"软合并"——靠模型的近因效应（recency effect）来倾向执行更近（更具体）的指令。

CLI 配置优先级（从高到低）：

  1. CLI 命令行参数
  2. 环境变量
  3. 项目级配置（.claude/settings.json）
  4. 全局配置（~/.claude/settings.json）
  5. 默认值

配置之间是"硬覆盖"（hard merge）——高优先级的值直接替换低优先级的值，不存在"模型裁决"。

CLAUDE.md vs 配置：两种完全不同的合并策略 =========================================== CLAUDE.md（软合并 — 模型裁决） ────────────────────────────── Managed → User → 项目根 → 子目录 → CWD 全部注入 system 字段，模型自行处理冲突 system: "...Managed指令...\n...User偏好...\n...项目规范...\n...CWD覆盖..." ↑ ↑ 模型可能忽略 近因效应 → 更可能遵守 CLI 配置（硬覆盖 — 代码裁决） ────────────────────────────── 默认值 → 全局配置 → 项目配置 → 环境变量 → CLI参数 高优先级直接替换低优先级，没有"模型决定"的余地 apiModel = default → "sonnet" → "opus" → ... → "haiku" ↑ 最终生效

近因效应 vs Lost in the Middle 是同一回事吗？ — 不是！

  • 近因效应（Recency Effect）：当指令冲突时，模型倾向于服从最后出现的指令。这是 CLAUDE.md 分层设计的依据——CWD 的 CLAUDE.md 放在最后，权重最高。
  • Lost in the Middle：模型对于中间位置的信息注意力下降，可能直接忽略。这是长上下文的通用问题，和"冲突"无关。

一句话区分：近因效应 = 冲突时听后来的；Lost in the Middle = 不冲突也可能看不到中间的。

  • src/core/prompts/system.ts — 搜索 claudeMdContent 的拼接位置，确认它被注入到 system 字段的哪一段

四、怎么控制大模型不执行危险操作？

在 Claude Code 中，防止大模型执行危险操作（如强制推送、删除文件等）的机制有几层？每层的强弱程度如何？

CC 采用三层防线，从软到硬：

三层防线：从软到硬 =================== 第1层：系统提示词规则（SOFT — 可以被绕过） ────────────────────────────────────────── "不要使用 git push --force" "不要删除 .env 文件" ↑ 自然语言约束，模型可能不遵守 第2层：工具可用性控制（HARD — 模型无法调用不存在的工具） ────────────────────────────────────────── 只暴露 Read/Write/Bash/Glob/Grep/... 模型不可能调用 "deleteRepo" 因为这个工具根本不存在 ↑ 结构性约束，模型无法突破 第3层：运行时权限检查（HARD — 即使调用了也被拦截） ────────────────────────────────────────── useCanUseTool() → 检查权限级别 Bash: "git push --force" → 拦截 Write: 删除 .env → 需要用户确认 ↑ 代码逻辑拦截，模型无法绕过

具体示例：

  • 第1层：system 提示词中写"Bash 命令不能加 --no-verify"，这是自然语言规则，模型大概率遵守但不是100%
  • 第2层：Tools 字段里只给 Bash 工具，没有 "Shell" 或 "SSH" 工具，模型结构上无法绕过工具白名单
  • 第3层：useCanUseTool() 在运行时检查 Bash 命令的参数，发现 --no-verify 则拒绝执行，这是代码级拦截
防线层机制强度可绕过？
第1层system prompt 规则软是（prompt injection）
第2层tool 白名单硬否（API 层面）
第3层运行时权限检查硬否（代码层面）

为什么不能只靠第3层（运行时拦截）？为什么还要第1层？

  • 第1层（提示词规则）是最经济的防线：它能让模型在99%的情况下主动放弃危险操作，避免无意义的工具调用和权限检查开销。
  • 如果没有第1层，模型会频繁尝试危险操作 → 每次都被第3层拦截 → 浪费 token、增加延迟、用户体验差。
  • 三层防线的本质：第1层减少试探次数，第2层缩小攻击面，第3层兜底最终拦截。

在 CC 源码中定位三层防线的实现：

  • 第1层：src/core/prompts/system.ts — 搜索 "NEVER""、 "MUST NOT" 等禁止性规则
  • 第2层：src/core/tools/index.ts — 查看当前会话暴露了哪些工具，工具白名单的决策逻辑
  • 第3层：src/core/permissions/useCanUseTool.ts — 运行时权限检查，搜索 processUserInput() 中的 hook 检查逻辑

本日小结

Day 03 核心知识图谱：

  1. API 请求结构：system / tools / messages 三个独立字段，分离是为了校验、缓存、防幻觉
