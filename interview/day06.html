Day 06 - 技能、斜杠命令与工具编排

1. /commit 为什么不直接在本地完成？

蚂蚁 字节 Senior
/commit 命令的本质是什么？为什么不把它设计成一个纯本地操作，直接生成 commit message 并提交？

/commit 的类型是 type: 'prompt'，它并不直接执行 git commit，而是生成一段预设 prompt 发送给 LLM。LLM 根据当前 diff 的语义推理出高质量的 commit message。

关键原因：

  1. Commit message 需要语义理解 — 简单的 diff 统计（如 "修改了 3 个文件"）无法替代 LLM 对代码变更意图的推理。LLM 能读出"修复了登录超时的 bug"而非"改了 timeout 变量"。
  2. allowedTools 限制 — /commit 配置了 allowedTools，只暴露 Bash/Read/Write 三个工具，比用户自由输入更可控，避免 LLM 在提交流程中做多余操作。
  3. 流程可控性 — 整个提交流程（读 diff → 生成 message → 执行 git commit）由 LLM agent 驱动，但工具权限被严格收窄。
误区：认为 /commit 只是 git commit -m "..." 的快捷方式。实际上它是一个 agent 子任务，LLM 在其中做了 diff 分析和语义推理。另一个误区是"所有斜杠命令都需要 LLM"——/clear 就不需要。

对比 /commit（type: 'prompt'）和 /clear（type: 'local'）的设计原则：

  • 确定性操作应该用 local 命令——清除上下文、切换主题这些操作不需要 LLM 判断，纯计算即可完成，不应该浪费 token。
  • 需要推理的操作才用 prompt 命令——如果操作的正确性依赖于对上下文的理解，就必须经过 LLM。
  • 这一原则可推广：任何系统设计 AI 交互时，先问"这个操作需要理解吗？"不需要就不该调用 LLM。

在 CC 源码中，斜杠命令的 type 字段决定了执行路径：

/commit (type: 'prompt') │ ├─→ 构建 preset prompt（含 diff 信息） ├─→ LLM 推理生成 commit message └─→ 通过 allowedTools 执行 git commit /clear (type: 'local') │ └─→ 直接调用本地函数清除上下文 （零 token 消耗，毫秒级完成）

2. 技能 = 斜杠命令的统一接口

Mid
CC 技能（Skills）和内置斜杠命令（如 /commit、/clear）是什么关系？为什么要这样设计？

createSkillCommand() 返回的命令对象类型为 type: 'prompt'，与内置命令使用同一套接口、注册在同一张命令表中。

两者的唯一差异：

  • source 字段：'builtin' vs 'skills'，标识命令来源。
  • 定义格式：内置命令用 TypeScript 代码定义，技能用 Markdown 文件定义。

设计洞察：统一接口优于特殊处理。技能不需要一套独立的注册/调度机制，它只需要"变成"一个斜杠命令，就能复用整个命令执行流水线。

内置斜杠命令 技能 (Skill) │ │ │ TypeScript │ Markdown │ 定义 │ 定义 ▼ ▼ 命令对象 ◄── createSkillCommand() ──► 命令对象 │ │ │ source: 'builtin' │ source: 'skills' │ │ └──────────┬──────────────────────────┘ │ 统一命令表 ▼ 命令调度器 (同一套执行流水线) │ ▼ type: 'prompt' → 发给 LLM type: 'local' → 本地执行
误区：认为技能是一个"插件系统"，需要单独的加载器和运行时。实际上技能只是命令表里多了一行记录，执行路径与内置命令完全相同。

这个设计对应一个经典架构模式：统一接口（Uniform Interface）。

  • REST API 的核心原则——所有资源用同一套 HTTP 动词操作。
  • Plugin pattern——插件不定义新协议，只填充已有接口。
  • 好处：调度器不需要 if/else 判断"这是内置还是技能"，降低认知复杂度，也降低扩展成本。

3. 怎么控制工具调用的 token 消耗？

快手 淘天 Senior
LLM 每次调用都需要把所有工具的描述塞进 prompt，工具越多 token 消耗越大。如何优化？

工具描述就是 token！ 每个工具的 name + description + input_schema 都占用 prompt 空间，这是隐性成本。

优化策略（从易到难）：

策略做法效果
a) 动态工具加载只给当前任务需要的工具立竿见影，prompt 缩短最多
b) 工具结果预算限制工具返回内容的长度防止单次调用撑爆上下文
c) 压缩工具描述缩短 description 文本边际收益递减，影响可读性
d) 模型路由简单任务用小模型 + 少工具全局最优但实现复杂

CC 的实践：allowedTools 配置在技能定义中，限制了 LLM 能"看到"的工具集合。比如 /commit 只暴露 Bash/Read/Write，其他十几个工具的描述完全不进 prompt。

全量工具 (20+ tools, ~8000 tokens) │ │ allowedTools 过滤 ▼ 技能可见工具 (3 tools, ~1200 tokens) │ │ 构建 prompt ▼ System Prompt + 工具描述 + 用户消息 → LLM 节省: ~6800 tokens/次调用

两个常见误区：

  1. 只关注工具调用结果的 token，忽略了工具描述本身就在消耗 prompt token——这是"固定成本"，不管工具是否被调用都要付。
  2. 认为工具越多越好。工具数量和 LLM 选择准确性负相关——工具越多，选错工具的概率越高，而且 token 成本线性增长。

更深层的优化思路：工具分层。

  • Core tools（Read/Write/Bash）— 几乎每个任务都需要，始终加载。
  • Domain tools（如 web search、database query）— 按技能/场景按需加载。
  • Niche tools（如特定 API 调用）— 极少场景使用，可延迟加载（甚至两轮交互：先让 LLM 声明需要什么工具，再注入）。

这本质上是"索引 + 按需加载"的思想，类似操作系统的虚拟内存——不是所有页都在物理内存里。

CC 源码中 allowedTools 的工作方式：

  1. 技能 Markdown 中声明 allowedTools: [Bash, Read, Write]
  2. 命令调度器读取该配置，在构建 LLM 请求时过滤工具列表
  3. 未列出的工具不出现在 system prompt 中，LLM 无法调用

这同时实现了两个目标：节约 token（少描述）和安全控制（少能力）。

4. 如何设计一个可扩展的工具注册系统？

Senior
如果你要设计一个支持动态添加工具（如 MCP 外部工具）的注册系统，核心接口应该怎么定义？

CC 的答案：Tool 接口 + 工具注册表 + 动态添加（MCP）。

核心接口定义：

interface Tool {
  name: string           // 唯一标识
  description: string    // 告诉 LLM 这个工具做什么
  input_schema: JSONSchema  // 参数结构，LLM 据此生成调用
  execute(params): Promise<string>  // 实际执行逻辑
  isConcurrencySafe: boolean  // 是否可并行调用
}

关键设计决策：

  1. 接口不依赖具体工具实现 — MCP 工具和内置工具实现方式完全不同（一个走网络协议，一个走本地函数），但对外呈现同一套接口。
  2. 注册表是唯一的真相来源 — 所有工具（内置 + MCP + 技能注入）都注册到同一张表，LLM 不需要知道工具来自哪里。
  3. 动态添加/移除 — MCP server 连接时注册工具，断开时移除，无需重启。
内置工具 MCP 工具 技能工具 │ │ │ │ Tool 接口 │ Tool 接口 │ Tool 接口 │ (本地函数) │ (网络调用) │ (受限子集) ▼ ▼ ▼ ┌─────────────────────────────────────────────┐ │ 工具注册表 (Tool Registry) │ │ │ │ name → Tool (统一接口，不区分来源) │ └──────────────────┬──────────────────────────┘ │ ┌──────────┼──────────┐ ▼ ▼ ▼ LLM 选择 权限过滤 执行调度 │ allowedTools 过滤 │ ▼ 可执行工具子集 → LLM prompt
误区：在 Tool 接口里加 source: 'builtin' | 'mcp' 字段来区分工具来源。这违反了统一接口原则——调度器不应该关心工具来自哪里，只需要知道它能不能执行、安不安全。来源信息属于元数据，不属于行为接口。

这是经典的 Plugin Pattern（插件模式）：

  • 核心不变：Tool 接口一旦定义，极少修改。
  • 扩展开放：新工具（MCP、第三方）只需要实现接口就能接入。
  • 修改封闭：添加新工具不需要改动注册表或调度器的代码。

进阶考量：

  • 工具冲突：不同 MCP server 可能提供同名工具。注册表需要命名空间（如 mcp__serverName__toolName）来避免冲突。
  • 工具能力声明：是否需要 capabilities 字段，让调度器在执行前判断工具是否满足当前需求？
  • 工具版本：MCP server 升级后工具 schema 变了怎么办？需要版本感知。

CC 源码中工具注册的实际流程：

  1. 启动时，内置工具（Read/Write/Bash/Glob/Grep 等）注册到 Tool Registry
  2. MCP server 连接成功后，调用 tools/list 获取工具列表，逐个转换为 Tool 接口并注册
  3. 技能激活时，根据 allowedTools 从注册表中筛选可用工具
  4. LLM 请求时，只有筛选后的工具描述进入 prompt
  5. MCP server 断开时，对应工具从注册表中移除

整个过程对 LLM 完全透明——它只知道"我有这些工具可用"，不关心工具的实现。
