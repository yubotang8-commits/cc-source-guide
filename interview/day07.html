Day 07 - 上下文管理（上）：5层渐进压缩防线

上下文窗口是 Agent 的"工作台"。聊得太长，工作台就乱了。Claude Code 的解法是一套 5 层渐进式压缩防线——先用免费的，再花小钱，再花大钱，实在不行就拒绝。这是 Agent 面试中被问得最多的问题。

1. 面试题：Agent 的上下文窗口怎么管理？聊太长怎么办？

Agent 的上下文窗口怎么管理？对话太长了怎么办？ 几乎所有公司都会问 字节 阿里 腾讯 mid

Claude Code 的答案是5 层渐进式压缩防线，逐层升级，成本递增：

  • Layer 1：时间检测（idle timeout）—— 免费
  • Layer 2：microCompact（规则压缩）—— 免费
  • Layer 3：sessionMemory（段落摘要）—— 便宜
  • Layer 4：autoCompact（全量摘要）—— 昂贵
  • Layer 5：blockingLimit（硬限拒绝）—— 无代价，但不服务

核心设计哲学：先用免费的，再花小钱，再花大钱，实在不行就拒绝。

误区：一上来就调大模型做全量压缩。
问题：1) 浪费钱——很多场景免费层就能搞定；2) 仍然可能超限——大模型压缩后的摘要本身也可能很长，全量压缩不是万能药。
正确做法：分层渐进，便宜的先上，不到万不得已不碰贵的。

2. 5 层渐进式压缩详解

Layer 1：时间检测（idle timeout）

触发条件：用户空闲 N 分钟（idle timeout）

成本：免费（不需要调用模型）

动作：清除消息中旧的工具调用结果（tool results）

源码位置：compact.ts

这是最"懒"的一层——用户都走了，旧的工具输出留着干嘛？直接清掉，不花一分钱。

Layer 2：microCompact（规则压缩）

触发条件：每次 API 调用之前

成本：免费（基于规则，不调用模型）

动作：用标记替换工具返回结果，例如：

  • 原来：Read a.txt 返回 15 行内容
  • 压缩后：[tool_result: Read a.txt - 15 lines]

关键洞察：确定性压缩，不需要 LLM 参与。工具的返回结果往往占上下文的大部分体积，但后续对话很少需要完整回顾。用一句话摘要替代整块输出，省下的 token 极其可观。

microCompact 压缩效果示意： 压缩前： ┌─────────────────────────────────────────────────────┐ │ user: 帮我看一下 a.txt │ │ assistant: [调用 Read("a.txt")] │ │ tool_result: │ │ 1 | import React from 'react' │ │ 2 | import { useState } from 'react' │ │ 3 | export default function App() { │ │ ... │ │ 15| } │ │ user: 再看看 b.txt │ │ assistant: [调用 Read("b.txt")] │ │ tool_result: │ │ 1 | const express = require('express') │ │ ... │ │ 30| app.listen(3000) │ └─────────────────────────────────────────────────────┘ 约 2000 tokens 压缩后： ┌─────────────────────────────────────────────────────┐ │ user: 帮我看一下 a.txt │ │ assistant: [调用 Read("a.txt")] │ │ tool_result: [Read a.txt - 15 lines] │ │ user: 再看看 b.txt │ │ assistant: [调用 Read("b.txt")] │ │ tool_result: [Read b.txt - 30 lines] │ └─────────────────────────────────────────────────────┘ 约 60 tokens

Layer 3：sessionMemory（段落摘要）

触发条件：消息逐渐变长时

成本：便宜（使用 Haiku 小模型）

动作：段落级摘要，对历史对话做分段概括

定位：这是 5 层防线中的中间层——不在原始 30 天指南中，但是 CC 实际存在的补充层。它填补了 microCompact 和 autoCompact 之间的空白：microCompact 只能压缩工具输出，对自然语言对话无能为力；autoCompact 成本太高，不该轻易触发。sessionMemory 用小模型做段落级摘要，成本可控且效果不错。

Layer 4：autoCompact（全量摘要）

触发条件：token 数超过阈值

成本：昂贵（使用 Sonnet 大模型）

动作：全量对话摘要——重写整个历史

定位：这是"核弹选项"——上下文已经长到小模型兜不住的时候，只能让大模型完整阅读并生成一份摘要，用摘要替代原始对话。消耗大量 token，但能把上下文压缩到很小。

Layer 5：blockingLimit（硬限拒绝）

触发条件：超过硬性上限

成本：无（直接拒绝服务）

动作：拒绝继续对话，提示用户开启新会话

这是最后的底线——连 autoCompact 都压不下来了，再继续只会出错。不如直接告诉用户"对话太长了，请开新会话"。

为什么不是 4 层或 6 层？
每一层都有明确的功能边界和成本跃升：
— Layer 1→2：从"用户走了再清理"到"每次调用前都压缩"，触发频率跃升
— Layer 2→3：从"不用模型"到"用小模型"，成本从 0 到低
— Layer 3→4：从"小模型"到"大模型"，成本从低到高
— Layer 4→5：从"花大钱解决"到"放弃治疗"，从"还能救"到"救不了"
每一层的存在都是因为前一层不够用了，而下一层又太贵/太晚。
源码追踪路径：
compact.ts 是核心文件。CC 在每次 API 调用前会检查是否需要压缩：
1. 先检查 idle timeout（Layer 1）
2. 执行 microCompact 规则替换（Layer 2）
3. 估算 token 长度，如果接近阈值 → sessionMemory（Layer 3）
4. 如果超过阈值 → autoCompact（Layer 4）
5. 如果 autoCompact 后仍超限 → blockingLimit（Layer 5）

3. 面试题：压缩失败会怎样？3 次熔断的工程细节

autoCompact 压缩失败会怎样？连续失败怎么办？ 字节 阿里 mid

CC 使用 consecutiveFailures 计数器 实现跨轮次熔断：

  • 每一轮：尝试 autoCompact → 如果收到 prompt_too_long 错误 → consecutiveFailures++
  • 如果 consecutiveFailures >= 3 → 触发熔断 → 返回"Conversation too long"错误
  • 一旦某轮 autoCompact 成功 → 重置 consecutiveFailures = 0

最特殊的情况是 prompt_too_long：压缩请求本身超过了 token 限制——这形成了一个catch-22：需要压缩才能继续，但压缩本身就需要太多 token。

3 次熔断机制： 第 1 轮对话 │ ▼ autoCompact → prompt_too_long → consecutiveFailures = 1 │ ▼ 第 2 轮对话 │ ▼ autoCompact → prompt_too_long → consecutiveFailures = 2 │ ▼ 第 3 轮对话 │ ▼ autoCompact → prompt_too_long → consecutiveFailures = 3 → 熔断！ │ ▼ 返回 "Conversation too long" 拒绝继续对话 ────────────────────────────── 如果中间某轮成功了： autoCompact → 成功 → consecutiveFailures = 0（重置）
"重试3次" vs "跨轮次累计3次"——完全不同！
— "重试3次"：同一轮内重试3次，如果都失败就放弃。但下一轮重新计数。
— "跨轮次累计3次"：CC 的实际做法。连续3轮对话都压缩失败才触发熔断。
区别在于：跨轮次累计意味着即使下一轮自动重试了，失败也会叠加。面试中如果回答"重试3次"就是踩坑。
prompt_too_long 的 catch-22 本质是什么？
上下文太长 → 需要压缩 → 压缩请求要发送整个上下文作为输入 → 上下文太长导致压缩请求本身也超限 → 压缩失败。
这是经典的自指悖论：解决方案本身就是问题的一部分。CC 的应对是：如果单次 autoCompact 失败，不会在同一轮无限重试（那只会反复超限），而是等到下一轮，看用户的新消息是否让情况有所变化。如果连续3轮都没救，才承认失败。

4. 设计题：你的 Agent 系统上下文管理策略是什么？

设计一个 Agent 系统的上下文管理策略，你会怎么做？ 阿里 字节 美团 senior

回答模式：先分层 → 再讲熔断 → 再讲系统提示词不参与压缩

第一，分层渐进压缩：

  • 免费层：规则压缩，不调模型。用标记替换工具输出、清除空闲数据
  • 低成本层：小模型做段落摘要，保主要信息，丢细节
  • 高成本层：大模型做全量摘要，保留完整语义
  • 拒绝对：超过硬限直接拒绝，不浪费资源

第二，熔断机制：连续压缩失败 N 次后触发熔断，避免无限重试消耗资源

第三，系统提示词不参与压缩：系统提示词是缓存的基础，压缩它 = 破坏缓存 = 后续每次调用都要重新发送完整系统提示词，token 消耗暴增

反模式：一上来就调大模型做全量压缩。
问题：
1. 浪费钱：Layer 1 和 Layer 2 是免费的，很多场景到 Layer 2 就够了，直接上 Layer 4 是拿大炮打蚊子
2. 仍然可能超限：大模型生成的摘要也可能很长，特别是对话涉及多个文件时
3. 延迟高：大模型压缩需要几秒到几十秒，Layer 2 的规则压缩是毫秒级
系统提示词为什么不能参与压缩？
核心原因是Prompt Cache。Anthropic 的 API 支持 prompt caching：如果 system prompt 没变，API 会缓存它的处理结果，后续请求直接复用缓存，省下大量 token 和延迟。
如果压缩了 system prompt：
— 缓存立即失效（因为 content 变了）
— 后续每次请求都要重新发送完整 system prompt
— system prompt 通常占 10K-30K tokens，每次重发成本极高
所以 CC 的设计是：系统提示词永远完整保留，只压缩对话历史。
源码中的体现：
在 compact.ts 中，autoCompact 的压缩范围不包含系统提示词。压缩函数接收的输入是 messages 数组（对话历史），system prompt 始终作为独立参数完整传入 API。这也是 CC 能有效利用 prompt caching 的关键设计决策。
