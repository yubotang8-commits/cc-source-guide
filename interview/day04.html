Day 04 - Prompt Caching：缓存统治一切

1. 什么是 Prompt Caching？为什么 Agent 系统特别需要它？

什么是 Prompt Caching？为什么 Agent 系统特别需要它？ 字节阿里腾讯 Senior

定义：Prompt Caching 是前缀缓存机制——API 自动缓存从请求开头到标记点（cache breakpoint）的所有 token。下次请求如果前缀相同，直接复用缓存，不需要重新计算。

Agent vs Chatbot 的根本差异：

  • Chatbot：用户聊几轮就结束，prompt 总量有限，缓存收益不大
  • Agent：连续工作几十轮，每次都要重发完整 prompt（system prompt + tools + history），token 量巨大

算一笔账：

场景Input Token轮数总 Token费用
无缓存100K353.5M极贵
有缓存（前 90K cached）100K（新 token 仅 10K）35~900K省 80%+

行业共识：Cache Rules Everything Around Me——缓存统治一切。字节、阿里、腾讯的 Agent 系统，缓存命中率是核心优化指标。

误区：认为 Prompt Caching 是"缓存整个请求"或"缓存某条消息"。

正解：缓存的是前缀（prefix）——从请求开头到第一个断点之间的连续 token 序列。只有前缀完全匹配才能命中缓存。

追问：为什么是"前缀缓存"而不是"任意位置缓存"？

答：因为 LLM 推理是自回归的——token 从左到右依次生成。缓存 KV cache 只能在已计算过的前缀上复用。中间某段匹配了但前面不同，KV cache 对不上，无法跳过计算。

2. CC 怎么设计 Prompt Layout 来最大化缓存命中？

Claude Code 怎么设计 Prompt Layout 来最大化缓存命中率？

CC 的核心策略：把静态内容放前面，动态内容放后面，只在静态部分的末尾标记一次 cache_control。

Prompt Layout（从上到下） ┌─────────────────────────────────────┐ │ System Prompt (STATIC) │ ← 缓存命中区 │ ├─ 角色定义 │ │ ├─ 行为规范 │ │ └─ 常量指令 │ ├─────────────────────────────────────┤ ← cache_control 标记点 │ ★ 缓 存 边 界 ★ │ ├─────────────────────────────────────┤ │ Dynamic Context (DYNAMIC) │ ← 每次请求可能变化 │ ├─ 当前工作目录信息 │ │ ├─ 附加消息（agent listing 等） │ │ └─ 其他运行时上下文 │ ├─────────────────────────────────────┤ │ Tool Definitions │ ← 缓存命中区（静态） ├─────────────────────────────────────┤ │ Conversation Messages │ ← 逐轮增长 └─────────────────────────────────────┘ 缓存命中流程： 第1轮：全部计算 → cache_creation（建立缓存） 第2轮：system prompt + tools 完全相同 → cache_read（命中缓存）→ 只算新增部分 第N轮：前缀不变 → 继续命中 → 越往后省越多

关键设计：cache_control 只标记一次——在系统提示词的最后一个块上标记。

误区：在每个块后面都标 cache_control，觉得"多标几个断点缓存更细粒度"。

正解：每个断点 +25% 费用。中间断点没有意义——因为前缀匹配规则，只有从开头完全一致的内容才能命中。标在中间只会多花钱，不增加命中率。

追问：前缀匹配规则具体怎么理解？

答：假设 prompt 分三段 A-B-C，缓存了 A-B。下次请求如果是 A-B'-C'（B' 和 B 不同），那么从 B' 第一个不同字符处开始，之后全部不命中。只有 A 能命中——从头到第一个不同位置之前的内容才能被缓存复用。所以中间的断点毫无意义，关键只有第一个断点（静态部分的边界）。

3. 频繁变化的内容怎么处理不影响缓存？

Agent 系统中频繁变化的内容，怎么处理才不影响缓存命中率？ 字节美团 Senior

核心技巧：把频繁变化的内容从 Cache 边界内移到边界外。

CC 案例：Agent Listing 的迁移

Before（缓存命中率低）： ┌──────────────────────────────┐ │ System Prompt │ ← static, cached ├──────────────────────────────┤ │ Tool Descriptions │ │ ├─ tool A: ... │ │ ├─ tool B: ... │ │ └─ agent listing (动态!) │ ← 每次可能变！ ├──────────────────────────────┤ ← cache_control │ Messages... │ └──────────────────────────────┘ 结果：agent listing 变化 → tool 块不同 → 前缀不匹配 → cache 命中率只有 ~10% After（缓存命中率高）： ┌──────────────────────────────┐ │ System Prompt │ ← static, cached ├──────────────────────────────┤ │ Tool Descriptions │ ← static, cached │ ├─ tool A: ... │ │ └─ tool B: ... │ ├──────────────────────────────┤ ← cache_control │ Attachment Message: │ │ "当前可用 agents: X, Y, Z" │ ← 动态内容移到这里！ ├──────────────────────────────┤ │ Messages... │ └──────────────────────────────┘ 结果：tool 块始终不变 → 前缀稳定 → cache 命中率大幅提升

原则："把频繁变化的内容从 Cache 边界内移到边界外"——动态内容放到 cache_control 标记点之后，这样即使它变了，前面已经缓存的前缀不受影响。

误区：觉得缓存命中率低是因为 token 太少，于是拼命在 system prompt 里塞更多内容。

正解：命中率低是因为前缀不稳定，不是内容不够多。塞更多内容如果包含动态部分，反而更不稳定。

4. CC 怎么知道缓存命中了？

Claude Code 怎么知道缓存命中了？

答案：它不需要在请求过程中知道。它只在事后通过 API 返回的 usage 字段发现。

{
  "usage": {
    "input_tokens": 5000,
    "cache_read_input_tokens": 90000,   // 缓存命中的 token 数
    "cache_creation_input_tokens": 0    // 本次新建缓存的 token 数
  }
}

这是 API 契约：CC 只负责标记 cache_control，服务器端处理缓存匹配和复用。CC 从不主动判断"这次能不能命中"——它只管按规范请求，通过 usage 字段观测结果。

协议思维：双方只关心接口规范，不关心内部实现。CC 不需要理解服务器的缓存淘汰策略、存储机制——它只需要知道"标记了 cache_control，服务器会尽量缓存；命中了会在 usage 里告诉你"。

追问：如果 CC 想主动优化缓存命中率（比如决定是否加 cache_control），它需要知道什么？

答：它需要知道前缀的稳定程度——如果 system prompt 在多轮对话中不会变，就值得标记 cache_control。如果知道某段内容每轮都变，就不应该放在缓存边界内。这些都是 CC 能在客户端侧判断的，不需要服务端信息。

5. 设计题：你的 Agent 系统怎么优化 Prompt Caching？

设计你的 Agent 系统的 Prompt Caching 优化方案。 Senior

CC 的完整答案：三层防御

第一层：Static/Dynamic Boundary

  • 严格划分静态区域和动态区域
  • cache_control 只标一次，标在静态区域末尾
  • 动态区域全部放在标记点之后

第二层：Minimize Dynamic Section Size

  • 动态区域越小，每次请求的"新 token"越少，费用越低
  • 如：agent listing 从 tool 块移到 attachment message，动态区域只多了一条消息

第三层：Avoid Timestamps/Random IDs in Static Section

  • 反模式：在系统提示词里嵌入时间戳或随机 ID
  • 后果：每次请求前缀都不同 → 缓存永远命中不了

CC 源码中的防御性编码：

CC 有一个变量名叫 DANGEROUS_uncachedSystemPromptSection——变量名本身就是文档！它警告每个开发者：这段内容不会被缓存，修改前请三思。这种命名方式强制代码审查者关注缓存影响，是一种工程防御手段。

对比朴素命名 extraPrompt：看不出任何风险信号。而 DANGEROUS_ 前缀就像代码里的红灯——你不能假装没看见。

完整优化策略全景： 输入层：System Prompt 设计 ┌──────────────────────────────────┐ │ 1. 静态/动态分离 │ │ static_block → cache_control │ │ dynamic_block → 不标记 │ ├──────────────────────────────────┤ │ 2. 动态区域最小化 │ │ 只放必须变化的内容 │ │ 能合并的合并，能省略的省略 │ ├──────────────────────────────────┤ │ 3. 静态区域纯净化 │ │ 无时间戳 ✗ │ │ 无随机 ID ✗ │ │ 无运行时状态 ✗ │ └──────────────────────────────────┘ 观测层：Usage 字段 ┌──────────────────────────────────┐ │ cache_read_input_tokens → 命中 │ │ cache_creation_input_tokens → 新建│ │ input_tokens → 未缓存部分 │ └──────────────────────────────────┘ 工程层：防御性编码 ┌──────────────────────────────────┐ │ DANGEROUS_ 前缀命名 │ │ → 代码审查时强制关注缓存影响 │ └──────────────────────────────────┘

误区：觉得缓存命中率高就够了，不用在意 cache_creation 的费用。

正解：cache_creation 的费用是正常 input 的 1.25 倍（每个断点 +25%）。如果缓存总是建了又失效（比如前缀不稳定），反而比不用缓存更贵。缓存的收益 = 多轮命中省下的钱 - 首轮创建多花的钱。

追问：如果你的 Agent 支持用户自定义 system prompt（每次可能不同），还值得做 Prompt Caching 吗？

答：分层处理——用户自定义部分放在 cache 边界之后，基础系统提示词保持静态。这样基础部分仍然可以跨请求缓存，用户自定义部分因为在前缀之外不会破坏缓存。本质还是 static/dynamic 分离思想——不是"全缓存"或"全不缓存"，而是最大化可缓存的前缀。
