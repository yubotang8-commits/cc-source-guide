Day 28 - Harness 设计思路

什么是 Harness

Harness 直译是"马具/安全带"。在软件中，它指"一个框架，用来跑和验证代码"。CC 的 Harness 是它的整体运行框架——怎么启动、怎么测试、怎么验证改动是否正确。

CC 的测试现状

根据项目文档，CC 目前没有统一的自动化测试套件。验证方式是：

CC 的验证策略： 1. 启动验证 └── bun run version → 能否正常启动并输出版本号 2. 手动测试 └── bun run dev → 启动交互模式 └── 操作你改动的功能，看是否正常 3. 针对性测试 └── 在改动模块附近写测试 └── 只测试你改的部分

为什么 CC 没有完整的单元测试

CC 的特殊性： 1. 终端 UI 难以自动化测试 └── 输出格式依赖终端宽度、颜色等 2. 大模型 API 调用不可预测 └── 每次回复不同，无法断言精确结果 3. 工具执行有副作用 └── 写文件、执行命令——测试后需要清理 4. 核心逻辑在 prompt 工程 └── 提示词的调整很难用断言验证 所以 CC 更依赖： → 冒烟测试（能不能跑起来） → 集成测试（核心流程走不走得通） → 手动验证（体验是否正常）

如果你要给 CC 加测试

推荐的测试分层： 第1层：冒烟测试（最基础） └── 程序能启动 └── 版本号能输出 └── 帮助信息能显示 第2层：单元测试（纯函数） └── messages.ts 的消息创建/转换 └── store.ts 的状态管理 └── config.ts 的配置解析 第3层：集成测试（带 mock） └── 模拟大模型 API 返回 → 测试 queryLoop 逻辑 └── 模拟工具执行 → 测试权限控制 └── 模拟 MCP 连接 → 测试工具注册 第4层：端到端测试（完整流程） └── 启动 → 输入 → 获取回复 → 验证输出 └── 这层最脆弱（依赖网络、大模型可用性）

开发工作流中的 Harness

开发流程： 1. 改代码 2. bun run version → 快速验证没崩溃 3. bun run dev → 启动开发模式 4. 手动测试改动点 5. 如果改了工具 → 测试工具调用 6. 如果改了提示词 → 测试对话质量 这个流程本身就是一种"轻量 Harness"
想象你在造一辆车： 完整测试 = 每个螺丝都测过扭矩（单元测试） 冒烟测试 = 点火看能不能发动（bun run version） 手动测试 = 开一圈试试（bun run dev） CC 目前的策略是：不测每个螺丝，但确保能发动、能开。 如果你要贡献代码，改了什么就手动测什么。
Harness 的核心思路：因为大模型的输出不确定，所以测试重点放在"流程是否走得通"而非"输出是否精确匹配"。
