Day 27 - 大模型调用（下）：重试与错误处理

哪些错误需要重试

API 调用可能遇到的错误： 1. 529 Overloaded ← 服务器太忙了 └── 应该重试，等一会就好 2. 429 Rate Limited ← 请求太频繁 └── 应该重试，减慢速度 3. 500 Internal Error ← 服务器出了 bug └── 可以重试，可能下次就好了 4. 401 Unauthorized ← API Key 不对 └── 不应该重试，重试也没用 5. 400 Bad Request ← 请求格式有错 └── 不应该重试，需要修代码

withRetry：自动重试机制

src/services/api/withRetry.ts 实现了重试逻辑：

withRetry(asyncFn, options) 第1次调用 │ ├── 成功 → 返回结果 │ └── 失败（529/429/500） │ ▼ 等待一段时间（指数退避） 第2次调用 │ ├── 成功 → 返回结果 └── 失败 │ ▼ 等待更长时间 第3次调用 │ ├── 成功 → 返回结果 └── 失败 → 报错给用户 指数退避：1秒 → 2秒 → 4秒 → 8秒 ... 每次等待时间翻倍，避免雪崩。

指数退避是什么

你去一家很火的餐厅： 第1次：排了10分钟，没位子 → 等一会再来 第2次：等了20分钟再来，还是没位子 → 等更久再来 第3次：等了40分钟再来 每次等待时间翻倍 = 指数退避（Exponential Backoff） 为什么不能每次隔1秒就试？ 如果1000个人都在1秒后重试 → 服务器又被打爆了 指数退避让重试"越等越久"，给服务器喘息时间。

错误分类处理

错误处理策略： 可重试的错误（529, 429, 网络超时） └── withRetry 自动重试 └── 达到最大重试次数 → 提示用户 不可重试的错误（401, 400, 403） └── 直接报错，不重试 └── 401 → 提示检查 API Key └── 400 → 提示请求格式有误 └── 403 → 提示权限不足 部分失败（工具执行出错） └── 不中断对话 └── 把错误信息作为 tool_result 返回给大模型 └── 大模型可以调整策略重试

大模型自己也有"纠错"能力

工具执行失败的流程： 大模型: 调用 Read("not-exist.txt") 工具结果: "错误：文件不存在" │ ▼ 大模型看到错误信息 │ ▼ 大模型: "文件不存在，让我先看看目录里有什么" └── 调用 Glob("*.txt") 查找文件 └── 找到正确文件后重新调用 Read 这是大模型级别的"重试"，和 API 级别的重试不同。
两层重试：API 层 withRetry 处理网络/服务器问题，模型层通过工具结果反馈处理逻辑问题。
